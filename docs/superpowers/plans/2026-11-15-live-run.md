# Live Wave 2 Run Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run every write function of `MoneyblocksVault` live on Mezo testnet, send each refusal as a real transaction that lands with status 0, confirm every result from receipts and chain reads, and produce a transaction table.

**Architecture:** A Python runner (`scripts/live_run.py`, new, untracked) sends transactions from the owner and operator keystores, checks each receipt, and runs a tie-out after every step. A separate checker in a fresh process re-reads the chain and builds the table. The dashboard is checked in live-read mode against the same vault.

**Tech Stack:** Foundry 1.9.0 (`forge`, `cast`), Python 3, Mezo testnet (chain 31611, `https://rpc.test.mezo.org`), the Vite dashboard in `/root/moneyblocks-spike/app`, agent-browser.

**Spec:** `/root/moneyblocks-research/debt-attribution-design.md` (whitepaper sections 11, 15, 16.4, 20, 28, 36, 39, 46 to 48).

## Global Constraints

- Testnet only (chain 31611). No mainnet transaction.
- No `git push`, no new commit, no public repo or hosting, no AKINDO submission.
- Every reported result comes from a receipt or a chain read. Fork tests and mocks are not live evidence.
- Keys stay in keystores. No key or password is printed or logged.
- A refused call is sent with an explicit gas limit so it lands with status 0. Its reason is decoded by replaying the same call at the parent block with `eth_call`. The table labels that decode separately, because this RPC has no `debug_traceTransaction`.
- Gas on this chain is negligible.

## Review Focus

1. A repay that leaves Trove net debt below 1,800 MUSD must be refused by Mezo. Covered in Task 6.
2. A repay while overhead interest is unfunded must be refused with `InterestUnsettled`. Covered in Task 6.
3. A close while block cash equals debt must succeed, and interest residue must go to overhead. Covered in Task 8.
4. Approving a waiting payment after its mandate expired or was revoked must be refused. Covered in Task 7.
5. MUSD sent straight to the vault blocks `sweepResidualMUSD` until `recoverUnallocatedMUSD` moves it. Covered in Task 8.

Each amount is checked against live state before its send. Each refusal must fail on the guard named here. The runner stops if another guard fires.

- [ ] Instant: operator `requestTransfer(3, vendor, 0.05)` executes, since it is under the 0.1 threshold.
- [ ] Refusals from the operator: 1.6 to vendor, `PerTransactionCapExceeded`; to an unlisted address, `RecipientNotAllowed`; amount 0, `ZeroAmount`. From the owner, `NotOperator`.
- [ ] Waiting X: `requestTransfer(3, vendor, 0.5)` is pending. `cancelPayment(X)` succeeds. Refusals: cancel again, `PaymentNotPending`; from the operator, `NotOwner`.
- [ ] Waiting Y: `requestTransfer(3, vendor, 0.5)` is pending. Refusal: `requestTransfer(3, vendor, 0.46)`, `PocketInsufficient`. `approvePayment(Y)` executes. Refusals: approve again, `PaymentNotPending`; from the operator, `NotOwner`.

- [ ] Revocation: waiting W (0.2) is pending. `revokeMandate(3)`. `approvePayment(W)` reverts with `MandateRevoked(3)`. `cancelPayment(W)` succeeds. A new request reverts with `MandateRevoked(3)`. Restore with `grantMandate(3, …)`.
- [ ] Recipient: waiting V (0.2) is pending. `setRecipient(3, vendor, false)`. `approvePayment(V)` reverts with `RecipientNotAllowed`. `cancelPayment(V)` succeeds. Restore the recipient.
- [ ] Expiry: `requestTransfer(4, vendor, 0.3)` is pending before block 4 expires. After expiry, `approvePayment` reverts with `MandateExpired(4)`, a new request reverts with `MandateExpired(4)`, and `cancelPayment` succeeds.

## Coverage target

- All 19 write functions have at least one successful transaction: `createMoneyblock`, `setRecipient`, `grantMandate`, `revokeMandate`, `setApprovalThreshold`, `fundPocket`, `fundOverhead`, `recoverUnallocatedMUSD`, `sweepBTC`, `requestTransfer`, `approvePayment`, `cancelPayment`, `openGroup`, `addCollateral`, `borrow`, `repay`, `closeGroup`, `sweepResidualMUSD`, `accrue`.
- Every reachable guard has a refusal sent on chain.

## Not covered live (stated in advance)

- `LedgerDirty` and `PendingRewards`: unreachable through normal flows.
- Liquidation: a Mezo-side event that needs an oracle move testnet does not allow.
- `TransferFailed`: needs a token that returns false instead of reverting.
- `LedgerMismatch`: needs an outside change to the Trove.

## Out of scope

Mainnet, AKINDO submission, push, public hosting, dashboard write actions (already covered on the fresh vault through the test bridge), and dashboard review of waiting payments (unit tests only).

## Size and time

About 80 to 95 transactions, about 40 of them refusals. About 20 minutes of chain time, plus waits of 60 s and 300 s and RPC retries.

## Execution method

Native (recommended). The run is one sequence on one chain state, so a fresh subagent per task adds context cost without adding evidence. The independent checker in Task 10 provides the outside check.
